## 1. Summary

State: the area is clean in structure and has no dead local functions. A scan of every local function in the large files found none that is unused. Comment style is mostly compliant. The remaining problems are size, copy-pasted helpers and a few stale hand-run diagnostics.

The KPI readers are not where run time is lost. The whole chain after the rollouts is cheap: KPI 1.0 min, DASH 0.1, WEAK 3.3, RPT about 0.3. policy_evaluation.mat is 22 MB and edge_map.mat 5.8 MB. The small `eval_detector_metrics*.mat` files are 5 KB, so reloading them costs seconds. The bootstrap calls in `measure_all_kpis.m` total a few seconds. Only these things are real time or memory:

- `analyze_weak_points.m:92` loads the 14 GB `data/policy_pools.mat` to read six small fields. It is most of the 3.3 min WEAK stage and a 14 GB RAM peak, which matters for the memory-overcommit bug (checklist item 11).
- `edge_map.m` takes 190 min. About 172 min of it is `policy_run_set` rollouts, which live in `decision/` and are outside this area. In this area, section 3 (the `det_frames` loop) takes 23 min, and the bootstrap sections 4-6 plus the check points take about 9 min with some recomputation. Potential saving is about 3-5 min for the bootstrap recomputation and up to 15-20 min for section 3, which must be measured first.

Top 5 proposals:
1. **E3**: cache the six `PP` fields analyze_weak_points needs, instead of loading 14 GB.
2. **E1/E2**: one shared `ternary.m` (29 copies repo-wide, 6 in this area) and a few other shared tiny helpers. About 150 lines go away and no behaviour changes.
3. **E6/E7**: split `edge_map.m` (1861 lines) and `demo_gui.m` (2720 lines) without behaviour change. Prerequisite: about 35 tests grep the source text of these files, so the tests need a source-reader helper first (E14).
4. **E4/E5**: remove the recomputed bootstrap verdicts in edge_map (a few minutes) and time the `det_frames` loop (E5).
5. **E10 and the DEFECTS section**: retire three stale hand-run diagnostics. Two of them overwrite `params.mat` in the working folder. Also fix the comment that swallowed code in `diag_path_loss.m:55` (D1) and the silent catch in `result_status.m:30-33` (D2).

## 3. DEFECTS (behaviour looks wrong; kept apart from the cleanups)

- **D1 `diagnostics/diag_path_loss.m:55`: a comment swallowed code.** The line reads `[s, r] = ndgrid(1:nS, rr);   % the geometries the cell flies s = repmat(s(:)', 1, reps); r = repmat(r(:)', 1, reps);`. The two `repmat` statements were on this line before commit bddd137 (12.10, "Airframe shadowing on flights..."; `git blame -L55,55`, and `git show 97a2ddd:code/diagnostics/diag_path_loss.m` line 48 has the code). Now `reps` is ignored: `n = numel(s)` at line 56 is `nS x nG` rather than `nS x nG x reps`, so the validation grid of the diagnostic flies each geometry once. The same pattern search over all `code/*.m` found no other swallowed statement. Fix: put the statements on their own line. Impact: only this hand-run diagnostic (its own `results/diag_path_loss.txt`); no chain stage; `test_core.m:6136` reads its source only for the units of the sweep.
- **D2 `evaluation/result_status.m:30-33` and `:99`: silent `catch` disables the staleness check.** If `detector_id(...)` or `fusion_model()` throws, `cur_det` stays `''`, and `id_check` returns `{}` (line 99 `if isempty(cur), return`). Then `results/latency.mat` and `results/edge_map.mat` of another detector are not flagged STALE, and KPI 7 and the edge-map details would read MET against a different detector. The age check (`t(f) < t(...)`) still works, but the identity check, which is the main guard (checklist 12/13 family), is off with no message. Fix: on catch, mark the identity-bearing files stale with the reason "detector identity not computable" (behaviour change: report it as a fix).
- **D3 `diagnostics/diagnose_antenna_fault_reward.m:39,71` and `validate_new_threats.m:20,27` overwrite `params.mat` in the current folder.** Both save a modified `params.mat` in a loop and restore it only at the end (no `onCleanup`; an error mid-run leaves a modified file). `params.mat` is a hash input (`params_id`, which `result_status.m:66` compares for KPI 3). Running one of them in a live worktree while a chain is running changes the file under the chain's workers (checklist 13/15). Additionally `diagnose_antenna_fault_reward.m:41` calls `quick_ber_with_iq`, which does not exist in the tree (only `link/quick_ber.m`), so the script cannot run. The same hazard exists, with a guard, in `gui/demo_gui.m:861 saveParams` (called every run from `simRun`, restored by `onCleanup` in `runOneRun:1090`): the GUI must be started from a bundle (`profiles/rx<n>`, `demo_gui('rx4')`) or a copy, never from a worktree whose chain is running. Fix for the scripts: E10 (retire).
- **D4 (latent) `map_survivability_boundary.m:296` and `experiment_survivability_options.m:40`: `evalc('init_params')` rewrites `params.mat` at the start of each of the two longest stages (SURV 386 min, SURV3 600 min).** `init_params.m:471` saves it. If `profile.json` or `init_params.m` differs from what A0 used (for example edited between A0 and SURV), `params.mat`, and with it `params_id`, changes silently in the middle of a chain. Not a bug while nothing is edited. Safer: load `params.mat` and assert its `params_id` equals A0's. This is a behaviour change, so decide separately.
- **D5 (cosmetic) `gui/demo_gui.m:822-835`**: `loadSurvReference` swallows a load error and the boot log then says "survivability_boundary.mat not found" (line 216), which misreports a corrupt file. No saved number is affected.
