# D126 (draft) - KPI 7: honest timing of the deployed cycle and performance-only caches

Branch `kpi7-p1`, from `d4623ed` (profile 1's code of record); the same change on `kpi7-p3`
from `81ecc06` (profile 3). Draft for registration before any rerun; nothing here has been run.

## 1. Why

KPI 7 is the decision latency per 20 ms cycle, registered as the sum of the cycle's timed
components (`measure_latency.m`), median < 10 ms (the low latency class of Oli & Mahalal 2025,
Table 8) and p95 < 20 ms (the decision period). Measured on an idle machine: profile 1 median
10.94 ms, p95 13.53 ms; profile 3 median 11.09 ms, p95 13.64 ms. The p95 passes, the median
does not. A read-only review of the cycle found two kinds of issue:

- **Fidelity of the measurement.** Each timed cycle called three policies one after the other
  (DQN, rule, deployed). With the deployed policy `dqn`, the deployed call repeated the DQN
  call on warm code and data, so the registered sum read about 0.5 ms optimistic. The glue
  between components (the detector's input tensors, the observation struct) was untimed. The
  GPU synchronization read the device handle (`gpuDevice`) inside the detector's clock every
  cycle. LAT's monitor settings lacked the pools' power factors (`PP.pw`), so its monitor took a
  slower path than the evaluated one.
- **Invariant work redone every cycle.** The policy is not the MLP (already plain matrix
  products, `dqn_dense.m`) but the monitor: the decision-layer constants built three times, the
  power-step mask of 36 configurations rebuilt with `strsplit`, about 20 feature-name lookups
  through `ismember`, name lists rebuilt, the onset fit's grid and class list rebuilt. The
  predictor rebuilt the frame layout (a `RandStream` included), the receive filter's taps and
  its group index sets on every call; the spectrogram rebuilt its window.

## 2. What changes

### 2.1 Honest timing (`measure_latency.m`, `lat_cycle.m`)

- One cycle is one function, `lat_cycle.m`: spectrogram, link features, MMSE predictor,
  detector, policy, in cycle order, with exactly one policy call.
- Each chain is a whole cycle timed in its own passes, with its own warm-up pass: the deployed
  chain (no other policy before it in the cycle), the DQN chain as selected, the rule with
  escalation. Before, all three policies ran in one cycle.
- The registered figure stays the **sum of the deployed chain's components**. The glue counts
  in the component it serves: the detector's input tensors in the detector, the observation in
  the policy (stated in the header).
- A wall clock around the whole deployed cycle is printed beside the sum (`wall (deployed)`,
  also on one core): a side reading without a verdict.
- The GPU device handle is read once per device pass; the synchronization waits on it.
- LAT's monitor settings carry `PPm.pw`, computed as `build_policy_pools.m` stores it, so the
  timed monitor reads the evaluated pools' path.
- The header states that the receiver's own estimators (BER estimate, post-combining SNR,
  spatial metrics: `extract_closed_loop_frames.m:300-338`) run in the receiver before the cycle
  and are outside the timed cycle.
- `results/latency.mat` keeps every field its readers read (`measure_all_kpis.m`,
  `export_report_numbers.m`, `demo_gui.m`); it adds `wall_dep_median_ms`, `wall_dep_p95_ms` (and
  the same under `single_core`) and `det_first`. Every printed line keeps its format; the wall
  lines are new lines.
- Diagnostic only: `DET_FIRST = true` before the run times the detector before the predictor
  (the two read nothing of each other), to see whether the predictor's thread restore slows the
  detector (2.67 ms isolated against 3.65 ms in the cycle). It writes to
  `results/kpi7/latency_det_first.*`, never to the record.

These changes will likely **add** about 0.5 ms to the deployed sum (the deployed policy no
longer runs warm after the DQN call; the glue is now timed), and remove the `gpuDevice` query
from the detector's clock.

### 2.2 Performance-only changes (default on)

Each is a cache of a value that depends only on its key; on a cache hit the function returns
exactly the value the per-call code computed for that key, so the outputs are bit-identical by
construction. The guard (section 3) checks it on the real cycle anyway.

| File | Cache | Key | Estimated saving per cycle |
|---|---|---|---|
| `decision_config.m` | the constants struct (built 3x per cycle) | none (constants) | 0.1-0.15 ms |
| `config_gain_db.m` | the power_control mask of the action list (pools without `pw`) | the action list | 0.3-0.6 ms without `pw`; with `pw` set in LAT the mask is not read |
| `feature_index.m` | name -> column map | `link_features('names')` (already kept) | 0.2-0.4 ms (about 20 lookups) |
| `temporal_evidence.m` | the class names `logp_k`; the name list built only when asked | class count | 0.05-0.1 ms |
| `idle_summary.m`, `window_cues.m` | the name lists | none (literals) | 0.01-0.03 ms |
| `onset_shape.m` | the fit's grid; `cellstr(string(classes))`; `setdiff(1:nr, a)` | window length; class list (value and type); antennas | 0.05-0.15 ms |
| `clean_ber_ref.m` | the table in the log domain per kind | the pools' table (reset with it) | < 0.01 ms |
| `mmse_predict.m` | groups (frame layout, `RandStream`), their index sets (`setdiff`, `cellfun(@mean)`), the filter's taps | every params field `frame_layout.m` and `groups` read; rolloff, span, sps | 0.3-0.5 ms |
| `mmse_predict.m` | the thread count is set to 1 and restored only when it is not 1 already | - | ~0 in the record's passes (computations still run on one thread) |
| `spec_image.m` | the Hann window | none | 0.02-0.04 ms |

`decision_config.m` holds other constants in the two profiles; the cache around them is the
same. Every other changed function file is byte-identical between the two branches (the guard and
its tests differ only in their base commit).

Together about 1.2-2.0 ms of the components, against the ~0.5 ms the honest timing adds. These
are estimates from the cost of the removed calls, not measurements.

### 2.3 Guarded options (default off, the guard decides)

Each can differ in the last bits for reasons outside our code, so each stays off unless the
guard reads it bit-identical on every compared output; switching one on is a later, separate
registration.

- `spec_image('direct', true)`: the centred STFT as one windowed FFT in place of
  `spectrogram()`'s input parsing (~0.3-0.6 ms). FFT batch plans can differ in the last bits.
- `mmse_predict('tail', true)`: filter only from the receive filter's memory before the first
  measured frame (frame k-1's last `numel(h) - 1` samples) instead of both frames (~0.05-0.15
  ms). Filtering from a later start gives the same sums only if `filter` accumulates each output
  in the same order whatever the start.
- `clean_ber_ref('interpolant', true)`: a kept `griddedInterpolant` in place of `interp1`
  (~0.03-0.06 ms). Identical only if `interp1` evaluates through the same interpolant.

Not changed: the thread setting of the predictor stays (results can depend on the thread
count), no MEX, no change of precision, nothing that is decided.

## 3. The guard (`kpi7_guard.m`) and the tests (`test_kpi7.m`)

`kpi7_guard(tree)` runs from the checkout and reads a finished tree's data (read only). The
code before the changes is every changed function file taken from the base commit by `git show`,
first on the path; the current code is the checkout's. Both run over:

- the 84 frames of `measure_latency.m` (its own setup and frames), every chain, the detector on
  the CPU, compared per cycle with `isequaln` on img, raw, idle, g, probs, maha, cfg, mem, info;
  the old code runs twice, so a field that is not deterministic is reported as such;
- a replay of the deployed policy on the tree's test pools (the single, combined and clean
  sets of `evaluate_policies.m`, test split, one pass), compared per cycle on obs, a, mem, info,
  and link_env's tables.

Any mismatch rejects the default changes; the guard then tries each changed file alone and
names those that differ. Each guarded option is accepted alone on the same terms. The
diagnostic order and `PPm.pw` are reported (identical, or decisions identical). The tree is
never written (Simulink's folders redirected, the threshold cache checked current, the tree
listed before and after). Verdict: `results/kpi7/guard_verdict.{txt,mat}` in the checkout.

`test_kpi7.m` compares every cached function with the base commit's copy on synthetic inputs,
cold, warm and after its key changes, checks the timing structure (the deployed chain alone in
its passes, one policy per cycle, the wall clock beside the sum, the GPU handle read once) and
that every reader of `latency.mat` finds its fields. `test_core.m`'s
`test_latency_times_predictor` reads the cycle from `lat_cycle.m`.

## 4. Record and reruns

- Today's readings stay on record as measured (profile 1: 10.94 / 13.53 ms; profile 3:
  11.09 / 13.64 ms), with this registration beside them.
- Only after the guard accepts the default changes on both profiles: LAT, then KPI, DASH,
  WEAK, RPT and BUNDLE rerun on both profiles. That rerun is final whatever it shows, pass or
  fail; no further change is made for KPI 7 on its account.
- No other stage reruns: every change is bit-identical on the decision cycle (the guard's
  verdict), so no decision, pool, policy or KPI other than KPI 7 can move.
